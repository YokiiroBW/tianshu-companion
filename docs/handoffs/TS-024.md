## 完成内容

- 新增 `src/tianshu_companion/direct.py`（`core.direct`，可信同产品 Python 端口）。
  复用主动联系模块的既有模式：显式登记、持久行、闸门决策、派发 attempt、
  `settle`/`retry`/`recover`/`tick`/`work`，以及 `metadata` 表中的**有界轮转扫描游标**。
- **分流判据**：只有「首 token 完全等于已登记命令名/别名」且「登记覆盖该平台与受众」且
  「`state="registered"`」且「`reply_to="bridge"`」的文本才被认领为功能指令。
  `/查询x`、`查询 天气`、`@bot /查询 天气`、`帮我查询一下天气` 都不是命令；
  `reply_to="core"` 的裸命令文本继续走陪伴链（`reason="reply_owner_core"`）。
  **功能指令不得因为聊天模型或渠道不可达而失败**：`test_direct_command_does_not_depend_on_platform_or_chat_model`
  在来源、记忆、网关全部不可用时命令仍 completed 且已送达。
- **参数形态由登记决定，永不猜测**：`token`/`integer`/`rest`，非法即
  `missing_argument:*` / `unexpected_argument` / `invalid_argument:*` / `invalid_choice:*`；
  非法参数**不执行、不调用模型**，用登记推导的 `usage` 行回复（`/查询 <subject> [<detail>]`）。
- **独立快速路**：不排聊天防抖、不建 `collections`、不占两个聊天轮次名额、不调聊天模型。
  执行在应用新增的 0.5 秒 `direct_worker` 里；两个聊天轮次都在 `generating` 时命令仍执行并送达；
  慢插件在途时普通聊天照常完成派发（均有回归）。
- **一次执行**：`core.direct_command`（命令入口）与 `core.capability`（Core 显式能力调用）
  带同一条 `message_key` 时折叠到同一个 `direct_requests` 行，`entries` 记录
  `["command"]`/`["capability"]`，只跑一次适配器、只投递一次；重复 SDK 事件幂等返回同一请求；
  同键异参报 `idempotency_conflict`；同 `message_id` 的更高 `revision` 是新版本并**取代**旧版本
  （未派发的旧版本直接 `superseded`），并发两个入口只有一个 `_claim` 成功。
- **唯一回复责任**：`reply_to="bridge"` 时 Core 返回给调用方的 `result` 与 `reply` 都是 `null`，
  回复走既有出站管线；`reply_to="core"` 时请求停在 `awaiting_core`，适配器若同时回包则该请求
  收口 `unknown`（不是在两条线上各答一句）；请求不能改自己的登记回复方。
- **不新建第二条消息出口**：`Direct.delivery_request` 生成冻结的已发布
  `conversation#send_request`，`turn_id` 是这条直接请求自身（它拥有自己的回复，不借陪伴轮次），
  `reply_id = digest([request_id,"reply"])` 稳定去重，`turn_sequence` 取自会话唯一串行计数器
  （聊天回复与功能回复不会互相超越），`command` 信封在**投递时**用请求上存的 `origin_ref` 现签
  （慢任务不继承过期 deadline）。桥接侧 `tianshu_nonebot.routing.BridgeDelivery` 直接复用
  `Bridge.send`（目的地核验、`reply_id` 去重、unknown 纪律全在既有代码里）。
- **授权只用本地事实**：派发前 `_claim` 在同一事务内复核会话未隔离、账号在该会话**已受理入站**
  建立的 actor/person 绑定、登记范围、`actor_allowlist`、角色与 binding；
  失败即 `cancelled` + `blocked_reason="authorization_revoked:<原因>"`，**不调用、不投递**。
  未知账号（该会话没有已受理入站）直接 `Fault("forbidden")`，绝不从 payload 推断身份。
  `core.capability` 字段集封闭：`persona`/`permission`/`affection`/`consent` 等未知字段一律
  `invalid_input`——**模型文本、好感度、前端字段不是权限**。
- **在途纪律**：每次派发恰好一个 attempt（`direct-attempt:<digest([request_id, attempt_no])>`）；
  超时/异常/重启记 `unknown`（`unresolved=true`）且**绝不自动重发**；

## 自评发现并修掉的缺陷：功能回执夺走在途聊天轮次的回复

这是本任务**自己引入**、并在集成复核里实测复现的一个回归，已修：

- **现象**：`Bridge.send` 对同一会话只接受**严格递增**的位置
  （`turn_sequence * 100 + segment_sequence`），更小的一律 `version_conflict`。陪伴链在**封盘时**
  分配 `turn_sequence`；功能回复在**投递时**从同一会话计数器取号。于是「先封盘、仍在生成」的
  聊天轮次会在功能回执之后投递，位置更低 → 被桥接拒绝 → 该轮落到
  `reconciling` / `delivery_unknown`，**用户丢了一条聊天回复**。
  复现脚本 `.runtime/probe_ordering.py`：修复前 `turns = [(1,'sent'), (2,'reconciling')]`，
  桥接只收到 `[301]`（功能回执），聊天回复从未发出。
- **修法**（两处，都很小）：
  1. `Direct.deliver` 把功能回复用掉的号记在会话上
     （`conversations.direct_sequence`）；
  2. `Core._deliver` 在投递时若发现本轮的号 `<= direct_sequence`，就把**整个轮次**
     挪到下一个空位（记在轮次上 `send_sequence`，同一轮的每个分段共用这个号），
     而不是被拒绝。功能回执**不必等聊天模型完成**（不排队），聊天回复**一条不丢**，
     共享出口仍只看到一个递增顺序。
- **修复后**：`turns = [(1,'sent'), (2,'sent')]`，桥接位置 `[301, 401, 402]`——功能回执在前，
  聊天轮次的两个分段仍在自己同一个号段里。
- **回归**：`tests/test_routing.py::test_a_functional_reply_never_costs_a_pending_chat_turn_its_reply`
  用真实 `Bridge` 同时接聊天出站与功能投递；该用例在修复前**失败**（同一断言
  `['sent','reconciling'] != ['sent','sent']`），修复后通过。`docs/routing.md` 新增
  「共用一个出口时的顺序」小节。

## 独立复核（只读对抗复核）结论

另启一个只读子代理按任务卡逐条对抗复核实现（不看文档只看代码）。结论与我处理：

- **H（公平扫描游标可能饿死）→ 不成立**：它的推理与自己的模拟不一致。我另写
  `.runtime/probe_scan.py` 穷举真实几何（规模 1–8、四种 position 形状含"全部同一毫秒"、
  `max_scan`∈{1,2,3,5}、包含"游标停在最后一行"在内的所有起始游标）共 **704 例**，
  没有任何一行永远扫不到。游标的"回退"就是回绕本身。已把该几何固化为回归
  `test_the_rotating_scan_reaches_every_request_in_every_geometry`。
- **C（`hand_back` 后重复事件会双答）→ 不成立，且相反做法才会真的双答**：`hand_back` 只在
  Core 回答 `owner="companion"` 时发生，而那时 Core **没有**创建 `direct_requests` 行、
  没有执行插件；「插件已执行」与「Core 回答 companion」互斥。对同一条消息版本重复决策反而会
  造成"已进聊天链 + 又执行一次"。现状是"一个消息版本一个持久决定"，已用断言固定
  （重复 capture 仍返回 `companion`，且 `direct_requests` 仍只有 1 行）。
- **测试质量问题（H2/H3/H4/L3/L4）→ 采纳并加强**：
  `test_two_entries_share_one_execution_*` 增加"只有一个请求行/一个 attempt/再派发一次仍只有一次
  执行"；新增 `test_concurrent_entries_share_one_execution`（两个入口真并发同时起）；
  并发用例改为两个 `create_task` 真重叠并断言 gate 未放行；
  桥接用例改为断言**入站文本集合**（`["/不存在","你好","早上好"]`）而不只是计数；
  `test_command_bypasses_*` 去掉不可falsify的断言，改为断言 inbox 里只有那一条既有消息；
  参数尾巴那条例外分支移出循环单独断言。
- **M（`retry(redeliver=True)` 不核对回执归属）→ 采纳**：现在要求最近回执的
  `reply_id`/`segment_sequence` 确属本次投递文档，别人的回执不能当作本次未执行的证明。
- **M（`conversation_mismatch` 与 `conversation_unmapped` 混为一谈）→ 采纳**：会话被重新映射时
  记 `blocked_reason="conversation_mismatch"`，不把回复发到别处也不谎称"会话不存在"。
- 复核方还指出它在本机无法运行 `git`（不在 PATH），因此无法独立核对 base→head 的 diff；
  该核对由交付包 `changes.patch` 与 `git rev-parse` 记录承担。

## 局限与下一步

1. **没有真实 GsCore/群管实现**：随包只有 `SyntheticPlugin`（只读查询 + 慢任务）。
   真实功能插件必须由功能产品通过同一 `execute` 端口注入；在接入前**不得**称任何结果为真实
   游戏结果。真实 GsCore 后端接入属跨产品缺口，已在 `BLOCKED.md` 登记。
2. **Core 与桥接分进程时的交付端口**：本任务交付的是同进程 `BridgeDelivery`
   （`Bridge.send`）与既有 `Sender` 客户端两种接法，但**没有**新增 Core→桥接的跨进程
   "把这条已完成的直接回复发出去" 协议文档。已发布 `text-dialogue/v1` 只有平台侧
   `conversation#send`，没有 Core→桥接的投递文档，因此 `delivery_port` 缺省时
   `contract_gap` 如实标注、请求保持 `not_started` 且不声称已回复。跨产品缺口见 `BLOCKED.md`。
3. **授权复核只覆盖本地权威事实**：远端（Memory/Platform）撤权若尚未到达 Core 本地，
   本模块不声称能复核；与 `proactive.guard` 同一已声明缺口。需要远端复核时由宿主注入异步校验器。
4. **命令名匹配是首 token 相等，不做同义词/模糊/大小写折叠**（明确取舍，不是遗漏）：
   含糊或错字文本按设计继续走陪伴链。
5. **单进程**：SQLite 单所有者，跨进程/多实例并发不在范围内；"两个入口并发"只在同进程内验证。
6. `reply_to="core"` 的登记目前只能由 Core 显式能力调用触发（快路不认领），
   陪伴轮次如何调用该能力属陪伴链既有职责，本任务不新增模型工具协议。
7. 迁移恢复须停机并隔离 DB/WAL/SHM；本轮只用合成数据库，未操作生产数据。

## 本机环境限制（详见 BLOCKED.md）

本机 DSH 文件沙箱一度拒绝对 mode `0o700` 目录做 `os.scandir`（`WinError 5`），而
`tempfile.mkdtemp` 与 pytest 的 `tmp_path` basetemp 恰好用该 mode；因此
`tempfile.TemporaryDirectory` / `tmp_path` 相关用例在**基线上同样失败**（同一批 nodeid），
pytest 的 basetemp 清理还会在 `pytest_sessionfinish` 抛 `PermissionError` 吞掉标准摘要。
本轮按 `EXECUTOR.md` 记录而不绕过：不改 `tempfile`/`sitecustomize`/ACL/测试断言，
改用 `.runtime/run_suite.py`（只读观察 `pytest_runtest_logreport`，不碰产品与测试）
记录真实通过数。本任务新增的迁移用例自带普通权限 scratch 目录（`.runtime/tests/`），
使备份/回滚断言**真实执行**而不是 ERROR。
会话文件策略放宽为 `danger-full-access` 后，同一条标准命令 `python -m pytest -q` 已全绿
（见上节），上述环境限制随之消解，仅作为过程记录保留。
