## 语义决策（写清楚，便于复核）

1. **身份 = `scope` + `request_id` + `operation`**，绑定 `canonical` 规范化后的
   `{operation, subject, content, from_config, revision_id, operator, expected, reason, note}`。
   含 `expected` 是刻意的：**"同一个 key + 不同 expected" 是另一个请求**，它必须照常撞 CAS，
   而不是因为"见过这个 id"变成成功。
2. **缺身份 = 拒绝**（`invalid_input`，不执行也不记账）。适配器层：CLI 未给 `--request-id`
   时生成一次性 id（语义等同"这次不去重"，命令仍可用），HTTP 端口把 scope 记为已鉴权服务。
3. **只有成功的执行才落账本行**，且与业务写入同事务。失败（含 `version_conflict`、
   `invalid_input`）不留半截事实，也不占用身份：调用方修正后可换新 `request_id` 重试。
   同键异摘要的拒绝**不会**覆盖原身份（原请求仍可重放）。
4. **导入保留既有幂等语义**：键是部署文档指纹（`persona_imports`），同一文档重放返回
   `skipped`；它不参与 `request_id` 账本，也不被账本覆盖——按卡"合理界定导入既有幂等语义"。
5. **`approve` 推进版本**：审批改变可见状态（`state`、`approved_at`、`approved_by`），
   所以与其它写入一致地推进 persona 版本；决定行仍只追加。两个操作者凭同一次旧读取各自
   批准同一份草稿时，后者得 `version_conflict`。
6. **备份标签**：仍是"一次打开最多一份、取本次跳升的最高结构步骤"。v8→v9 得
   `pre-persona-ops-v9`；v7→v9 得 `pre-persona-v8`（v8 是它跨越的最高人格步骤）。
   本轮**未改**该既有流程，只更新断言与文档。

## 风险与缺口（本轮）

1. 账本只对**成功执行**记账；失败的请求不占身份，也不产生"失败结果重放"。
   若协调方要求"同一 key 的失败结果也必须重放"，需要另行定义失败的持久语义（当前未做）。
2. 账本行随写入增长且**不做清理**：与其它 persona 历史一样是仅追加证据，
   受 `MAX_REVISIONS_PER_ACTOR` 等既有上限约束的是修订/角色，不是账本行数。
   若长跑的运维写入量需要归档策略，应作为后续卡设计（本轮不引入裁剪，以免丢证据）。
3. 跨进程并发仍在范围外（`Store` 单所有者 + 进程内 `expected` CAS），与上一轮一致。
4. 跨多版本升级仍只取一份恢复备份（既有语义，未改）。
5. 本轮不是验收结论，也未做真实模型/渠道/前端；`approve` 版本推进属于**语义变更**，
   若协调方希望审批不推进版本，需要重新定义并发语义后再改。
