## 1. 做了什么

在**既有的**人格管理端口 `POST /internal/v1/persona/manage` → `Core.manage_persona` →
`Personas.manage` 上新增四个**只读**操作，让未来的统一网页可以直接消费"有界目录 / 单一历史种类
分页 / 单条不可变修订 / 两个版本比较"，而不需要第二条管理入口、第二个人格库或新的权限系统：

| 操作 | 语义 |
| --- | --- |
| `catalog` | 实时 keyset 角色目录（subject 升序，游标 = 最后已返回 subject，`consistency="live_keyset"`，不承诺跨页快照），不携带 persona/tone/style/address 正文 |
| `history_page` | 指定 subject + 一种 kind（`revisions`/`publications`/`approvals`/`rollbacks`）的有界页；游标绑定 subject/kind/`persona.version`/limit/last_key，版本变化即 `version_conflict` |
| `revision` | subject + revision_id 的单条不可变修订（正文 + fingerprint + 当前指针定位，同一读事务）；跨角色 `invalid_input`、未知 `not_found` |
| `compare` | 同一 subject 的两个修订，比较域固定 `persona`/`tone`/`style`/`address`，给出 presence/change/完整左右值 + 扩展字段摘要级结论；`identical_revision` 只看 id，`content_identical` 只看全正文 fingerprint |

## 4. 关键设计决定（可复核）

1. **只读与写入彻底分离**：四个读操作不带 `request_id`，不写业务事实、不写操作账本、不推进
   `persona.version`、不动指针。测试在读前后对比全部 `PERSONA_TABLES` 行数、`source_head()`、
   各角色版本与账本行数。
2. **有界性靠 SQL `LIMIT`，不靠 Python 切片**：`_page_rows` 用 `WHERE conversation_id=?` +
   `(position,id)` keyset + `ORDER BY position,id LIMIT ?`；目录用 `ORDER BY id LIMIT ?`。
   测试用 `set_trace_callback` 证明：**页读的 SQL 语句数不随历史长度变化**（4 条 vs 34 条历史同为
   7 条语句 / 3 条记录），且触及 persona 历史表的语句全部含 `LIMIT`、目录语句不含 `OFFSET`。
3. **版本失效来自既有语义**：`draft`/`approve`/`reject`/`publish`/`rollback`/`retire`/`restore`
   都经 `_save` 推进 `persona.version`，因此把 history 游标绑定到该版本即可覆盖卡列出的全部失效来源；
   旧页返回 `version_conflict` 并要求重开第一页，不拼接两版事实。
4. **`_approval` 改为索引单行读**（`(position,id)` 逆序 `LIMIT 1`，走既有
   `persona_approvals_revision` 索引）：与原来"整表载入后取最后一条决定"语义一致，
   但让 `get`/`state`/`publish`/目录/历史页都不再受决定表长度影响。既有 56 个 persona 用例全部通过。
5. **游标不落库**：进程随机 HMAC 密钥，重启即失效（明确要求重开第一页），不新增存储表、不写凭据、
   不携带正文。`issue_cursor` 要求绑定字段集合精确匹配，防止未来悄悄加字段绕开校验。
6. **比较不做泛化 diff**：固定四字段，O(两端正文长度)；正文允许的其它 scalar 字段只按规范化摘要
   比较并给有界字段名，`additional_fields_changed` 明确区分"四个字段都没变但扩展字段变了"，
   绝不输出"人格完全相同"。`compare` 不调模型、不打分、不批准。
7. **超预算只拒绝不截断**：页按实际 UTF-8 JSON 字节 ≤256 KiB（预算减去 `CURSOR_RESERVE` 后再对成品
   响应断言一次），单条修订/比较 ≤1 MiB，超限 `invalid_input`；页只在预算内收完整条目并给准确
   `next_cursor`（同时 `has_more=true`）。

## 7. 过程中发现的既有环境事实（未擅自扩大范围修复）

- Windows 上 `persona_cli` 把含中文的结果 `print` 到**被捕获的管道**时，子进程按本机代码页编码，
  而消费者按 UTF-8 解码会失败。这是 Python 在无控制台时的标准行为，与本卡改动无关；
  **HTTP/JSON 端口始终 UTF-8，不受影响**。处理方式：只在本任务的测试/探针里给子进程显式
  `PYTHONIOENCODING=utf-8`，未改 `persona_cli` 的输出编码（改它会破坏交互式控制台的中文显示），
  也未改任何既有断言语义。若协调方希望适配器在非控制台也固定 UTF-8 输出，建议另开卡。
