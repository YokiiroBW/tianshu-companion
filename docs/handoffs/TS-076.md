## 1. 做了什么

在**既有的**人格管理端口 `POST /internal/v1/persona/manage` → `Core.manage_persona` →
`Personas.manage` 上新增四个**只读**操作，让未来的统一网页可以直接消费"有界目录 / 单一历史种类
分页 / 单条不可变修订 / 两个版本比较"，而不需要第二条管理入口、第二个人格库或新的权限系统：

| 操作 | 语义 |
| --- | --- |
| `catalog` | 实时 keyset 角色目录（subject 升序，游标 = 最后已返回 subject，`consistency="live_keyset"`，不承诺跨页快照），不携带 persona/tone/style/address 正文 |
| `history_page` | 指定 subject + 一种 kind（`revisions`/`publications`/`approvals`/`rollbacks`）的有界页；**响应自带 `subject`/`kind`/`persona_version`/`consistency="version_bound"` 读取基准**；游标绑定 subject/kind/`persona.version`/limit/last_key，版本变化即 `version_conflict` |
| `revision` | subject + revision_id 的单条不可变修订（正文 + fingerprint + 当前指针定位，同一读事务）；跨角色 `invalid_input`、未知 `not_found` |
| `compare` | 同一 subject 的两个修订，比较域固定 `persona`/`tone`/`style`/`address`，给出 presence/change/完整左右值 + 扩展字段摘要级结论；`identical_revision` 只看 id，`content_identical` 只看全正文 fingerprint |

## 4. 关键设计决定（可复核）

1. **只读与写入彻底分离**：四个读操作不带 `request_id`，不写业务事实、不写操作账本、不推进
   `persona.version`、不动指针。测试在读前后对比全部 `PERSONA_TABLES` 行数、`source_head()`、
   各角色版本与账本行数。
2. **有界 = `LIMIT` + 匹配索引的范围 seek**：`_page_rows` 用行值谓词
   `WHERE conversation_id=? AND (position,id)>(?,?) ORDER BY position,id LIMIT ?`，与
   `persona_<kind>_page(conversation_id,position,id)` 完全匹配；目录用主键索引顺序 `ORDER BY id LIMIT ?`
   （首屏 `LIMIT` 即停，后续页 `SEARCH … (id>?)`）。测试断言四 kind 首/末页计划与 VM 步骤数，
   并断言目录无排序、无 offset。
3. **读基准随页返回**：`history_page` 每页都带 `subject`/`kind`/`persona_version`/`consistency`，
   与页记录、修订/审批投影同一短只读事务形成；版本失效仍来自既有 `_save` 推进 `persona.version`
   （draft/approve/reject/publish/rollback/retire/restore 全覆盖），旧页 `version_conflict` 并要求重开第一页。
4. **游标结构先于密码学**：ASCII 与 base64url 形状在 `base64`/`hmac`/`compare_digest` 之前判定，
   因此畸形输入永远是领域可映射的 `invalid_input`，不会变成 500；游标仍是进程随机 HMAC、
   不落库、重启即失效，不新增存储表。
5. **`_last_decision` 索引单行读**：`(position,id)` 逆序 `LIMIT 1`，走既有
   `persona_approvals_revision`（`read-bounds.log` 中计划为 `SEARCH … USING INDEX
   persona_approvals_revision (<expr>=?)`）；`get`/`state`/`publish`/目录/历史页都不再受决定表长度影响。
6. **派生索引只在既有索引区、只增不删**：`IF NOT EXISTS` 位于每次打开都会执行的索引创建路径
   （非迁移步骤），因此**已是 v9 的库**下次打开即补上，不产生备份、不改 `user_version`、不动事实，
   重复打开幂等（`test_opening_a_v9_database_adds_the_paging_indexes_without_touching_its_facts`）。
7. **比较不做泛化 diff、超预算只拒绝不截断**：比较域固定四字段，扩展字段只按规范化摘要比较；
   页 ≤256 KiB、单条 ≤1 MiB 按实际 UTF-8 JSON 字节，超限 `invalid_input`，绝不发不完整 JSON。

## 7. 过程中发现的既有环境事实（未擅自扩大范围修复）

- Windows 上 `persona_cli` 把含中文的结果 `print` 到**被捕获的管道**时，子进程按本机代码页编码，
  而消费者按 UTF-8 解码会失败。这是 Python 在无控制台时的标准行为，与本卡改动无关；
  **HTTP/JSON 端口始终 UTF-8，不受影响**。处理方式：只在本任务的测试/探针里给子进程显式
  `PYTHONIOENCODING=utf-8`，未改 `persona_cli` 的输出编码（改它会破坏交互式控制台的中文显示），
  也未改任何既有断言语义。若协调方希望适配器在非控制台也固定 UTF-8 输出，建议另开卡。
- Windows 上服务进程退出后，owner 锁的释放可能滞后于进程退出若干毫秒；测试的 `open_owned()`
  在既有的 SQLite 瞬时错误重试之外，也重试 owner 锁未释放这一情形（上限 5 秒，仍会如实失败）。
