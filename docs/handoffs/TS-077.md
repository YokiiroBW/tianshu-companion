## 1. 做了什么

在既有 `core.life` 可信端口之外新增一个**只读**内部 HTTP 端口，让已登记的外部读取服务读取
角色生活状态与**已发布**日记。四个操作（全部 POST，统一 `schema_version=1` 信封）：

| 路由 | 语义 |
| --- | --- |
| `/internal/v1/life-read/actors` | 只枚举「在 `life_readers` 部署表内 **且** 当前有剧情授权」的角色，actor_id 码点升序 keyset 分页 |
| `/internal/v1/life-read/snapshot` | 读**持久行**的角色状态（活动/心情/穿搭/房间/世界/版本），`state_basis="last_persisted"`，**不 tick** |
| `/internal/v1/life-read/diaries` | 只列 `published_revision` 非空的日记，`(day,diary_id)` 降序 keyset 分页，只给捕获标记不给正文 |
| `/internal/v1/life-read/revision` | 按已发布指针读**该**修订正文与捕获证明（配方/素材哈希/网关配置版本），先比版本再读正文 |

授权模型：凭据（`tokens`）确定调用服务名 → `life_readers` 确定该服务的固定 `reader_id` 与可见
actor 集合 → 每次请求实时读 `life_access` 剧情授权。请求体里的 `reader_id` 直接 400，
未知 actor 与无授权 actor 同为 404，不泄露存在性，撤销授权立即生效。

## 4. 关键设计决定（可复核）

1. **不 tick**：`Life.snapshot` 会 `tick(force=True)`（`life.py:381`），因此本端口只读持久行；
   `state_basis="last_persisted"` 明确写出这一点，`activity` 就是行里的当前值。
2. **读路径零写入**：`store.transaction()` 是 `BEGIN IMMEDIATE` 且推进 `source_head`，因此读路径
   走独立的短 `BEGIN`/`COMMIT`。测试对比读前后**全部事实表行内容**与 `source_head()`；
   真实 TLS 进程用例还在进程外逐字节对比。
3. **身份只能来自凭据**：`reader_id` 来自部署表并按服务名索引；请求体出现 `reader_id` 即 400。
   同一 `reader_id` 不得挂在两个服务上（否则一份授权会被两份凭据继承）。
4. **不泄露存在性**：未部署 actor、无授权 actor、非已发布修订一律 404；`life_access` 每请求读。
5. **版本先行**：`expected_diary_version` 不匹配时在读取任何 `life_revisions` 之前返回 409
   （用例用记录型连接断言此刻没有任何 revision 语句）。
6. **捕获证明来自真实回执**：`captured.config_version` 沿父链取最近一次网关生成的
   `model#route_receipt`，经已发布合同校验、要求 `caller_service="companion"`、
   `outcome="succeeded"`、正整数且与日记行一致；人工修订继承父证明。回执里的 `request_id`
   是模型侧随机 id，**故意不**与日记 id 比较。断链/环/异日记/素材不符/配置漂移一律 503；
   链长 >64 为 429。绝不把「重试后换过配置的日记」按新配置重新标注。
7. **分页是位置而不是引用**：游标是 `(day, diary_id)` 排序键，行被删除后仍可继续翻页；
   `limit`/游标显式传 `null` 与 bool 一样拒绝——缺省是缺省，`null` 是错误。
8. **预算宁可拒绝不截断**：原始请求体 16,384 字节在解析前按累积字节判定；`diaries` 262,144、
   `revision` 1,048,576 按整份 UTF-8 JSON 字节判定，超限 429 且不发半个文档。
9. **派生索引是唯一持久结构变化，且必须在有事实的库上留恢复点**：定义与卡内逐字一致，
   `IF NOT EXISTS`，不改表/字段/版本；比对 `sqlite_master` 时 SQLite 会把 `IF NOT EXISTS`
   规范化掉，因此 `shape()` 规范化空白与关键字大小写、但**对引号内 JSON 路径严格**；
   同名不同定义拒绝启动。缺索引时先 SQLite backup（含 WAL）到唯一
   `<database>.pre-life-read-index-<uuid>.bak`，失败即中止本次打开、不执行新 DDL；
   新空库/`:memory:` 不备份；v1..v8 打开已有本次 DDL 前的完整备份，直接复用不再多造一份。
10. **查询计划有界**：分页 SQL 与索引逐字匹配，计划为
    `SEARCH life_diaries USING INDEX life_diaries_published_page (conversation_id=?)`，无 TEMP B-TREE；
    实测 VM 步数在 20/2,000/20,000 条**其他角色**行下均为 **152**（keyset 页 339），
    在**本角色未发布**日记 40/4,000 条下同样为 **152**；删掉该索引后同一页退回
    `life_diaries_queue` + `USE TEMP B-TREE FOR ORDER BY`，步数 767 → **24,527**（见
    `.runtime/dsh-delivery/logs/read-bounds.txt`）。

## 7. 过程中发现的既有环境事实（未擅自扩大范围修复）

- Windows 上把子进程 stdout/stderr 接到**无人读取的管道**，日志写满管道缓冲后子进程会阻塞在写日志上，
  表现为「服务在某个请求后不再响应」。这只影响测试脚手架；本次真实进程用例改为把服务日志写入文件，
  并在断言失败时读回尾部，不再把管道填满当成服务故障。
- `Store` 的 sqlite 连接绑定创建线程，因此不能「在主线程建 `create_app()`、在另一线程跑 uvicorn」；
  另外真实进程用例的子进程必须先在同一线程内建应用（本卡按 uvicorn CLI 启动，不受影响）。
