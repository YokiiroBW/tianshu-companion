## 2. 日志语义（本卡的核心承诺）

- **全覆盖，不采样**：`EVENTS` 是静态登记表，未登记的名字直接 `ValueError`；每次失败都记，
  不做去重或"已见过"抑制。
- **秘密不可能被顺手写入**：记录只有 11 个封闭字段，没有 message/extra/堆栈/正文位置；
  异常文本永不写日志，失败只用异常**类型**查表得到的固定标签。
- **探针纯粹只读**：`/health/live`、`/health/ready`、`/healthz` 不写记录（中间件按
  `health.PROBE_PATHS` 放行），日志目录在探针前后逐字节一致。
- **容量失败不假装就绪**：预算写满 ⇒ 业务 503 + `x-tianshu-log-capacity-exhausted:
  exhausted`，`/health/ready` 报 `logs=failed`、`not_ready`。
- **日志失败不触发重发**：写入失败不向业务抛异常，在途副作用不因日志失败而重做；容量耗尽
  在受理之前拒绝，因此不存在需要重试的东西。
- **空闲与启动噪声不记录**：空闲轮次、7 个循环的启停都不写记录。这不是省事，而是必要：
  这些记录写在进程开始服务**之前**，在通道有硬上限时（4 KiB 管道）会把启动卡死——本卡
  实测过一次（子进程停在 4034 字节、端口始终不开），去掉后同一探针 0.53 秒内就回答了。
- **受理先于副作用（R1）**：业务请求在**执行任何副作用之前**先等一次真实落盘（`await
  obs.admit(...)`）。拿不到受理就不执行业务，返回 503 与真实原因码，绝不"先做后记"。
- **终态是真实终态（R2）**：记录里的 outcome 由领域状态映射而来（`send_receipt`、
  `cancel_response`、`turn.delivery_state`、attempt 状态），映射表封闭；没有映射的领域状态
  被拒绝并计数，绝不会被写成 `succeeded`。
- **有界单写者（R3）**：所有写入只发生在适配器自己的线程里，队列有界，业务循环永不等待同步
  IO，队列满即拒绝并计数（不静默丢弃），关闭有界且不与活动句柄竞态。句柄只由写者持有和释放，
  关闭是**一个有界动作**；超时如实返回"未确认"，不抢句柄、不清零在途计数。
- **停止是状态，不是队列条目（第三次返修 R1）**：停止意图由写者自己读取，队列满时哨兵塞不
  进去也不影响退出；IO 恢复后线程真的结束，不需要任何人手工补信号，重复关闭按当下事实回答。
- **关闭期限覆盖真正的 IO（第三次返修 R2）**：`close()` 在状态锁外执行，锁只用于交换引用；
  关闭方在**自己的** 30 ms 预算内给出结论，不会被一次 250 ms 的慢 `close()` 拖住。
- **容量基准先于受理（第二次返修 R1）**：构造时（启动路径）扫描既有分段建立预算基准，
  `submit` 与写者用同一条预算，预满目录的第一次 `admit` 就是拒绝，重启买不到容量。
- **终态持久（第二次返修 R3，第三次返修补齐后台接缝）**：终态记录由写者补 `fsync` 后确认，
  `fsync` 在写者线程上，业务接缝与权威事务不等待磁盘。终态**按含义**定义并双向锁住：请求/
  轮次/尝试/投递的结束、后台每一轮的真实工作与失败、取消、延后投递、出箱扫描、鉴权通过与
  进程停止；只宣告未完成工作的 `…started`/`turn.prepared`/`turn.queued` 不是终态。
- **日志失败不等于业务重做（R1/R3）**：记录写不进去时，已经在途的副作用不会被重发；业务只
  看到"日志没写成功"。

## 3. 验证（实际命令与实际结果）

### 第四次返修后（当前）

复验只留一个阻断：**owner 退出与 join 之间的引用竞态**。`_shutdown` 先判断
`self._writer is not None and self._writer.is_alive()`，再投递唤醒，之后**又一次解引用**
`self._writer.join(...)`；而 owner 自己在退出路径 `_release_stream()` 里会把 `self._writer`
置为 `None`。只要 owner 正好在这两步之间正常退出，关闭方就在 `None` 上调用 `join`，抛出
`AttributeError: 'NoneType' object has no attribute 'join'`——一个并发退出会变成关闭异常，
而且此时关闭**本来已经成功**。

修法：关闭在设置 `_shutdown_started` 的**同一次持锁**里取一次 owner 引用（局部变量），之后
的存活判断、唤醒投递与 `join` 全部只用这个引用；`stopped` 也由同一个引用得出。
`_writer_alive()` 同样改为"读一次引用、给一个答案"，避免同一次判断里读到两个不同的值。
按同样原则复核了本改动范围内的 owner 存活读取（`flush`/`await_flush` 的 `self._writer is None`
前置判断、`_release_stream` 的持有者检查、`_join_writer`）：它们只做"有没有 owner"的存在性
判断、不跨调用保留引用，因此不受该竞态影响，本轮不改；单 owner 释放、总期限与"未确认"语义
全部保留。

四点的修法与根因：

1. **R1 容量基准**：`submit` 曾按构造时的 `_directory_bytes = 0` 记账，而扫目录发生在写者的
   `_open` 里，于是满目录重启后**第一次受理**成功并越界 356 字节。现在适配器在**构造时**
   （启动路径，不是请求路径）就扫描既有分段建立基准，`submit` 用"基准 + 待写 + 新记录"判预算，
   写者追加前用同一条预算复核。度量**不创建目录**——只读探针构造适配器不会在文件系统上留下
   任何东西（`tests/test_health.py` 的"探针不建目录"用例锁住这一点）。
2. **R2 单 owner 单期限**：`aclose` 曾先 `_join_writer` 再同步 `close`，两次等待后仍关闭了活跃
   句柄，写者随后把 `_pending` 减成 -1。现在整个关闭是**一个**有界动作（排队 → 等写者 → 哨兵
   → join → 释放句柄），句柄只由写者持有和释放；超时返回"未确认"，不清零在途计数、不抢句柄、
   不丢写者引用。`aclose` 取消只停止等待，已启动的那次关闭仍会跑完。
3. **R3 终态持久**：终态事件（请求/轮次/尝试/投递结束、`runtime.stopped`）由写者写完后再
   `fsync` 才确认，`fsync` 发生在写者线程上，业务接缝与权威事务不等待磁盘。另外修掉一个连带
   缺陷：`_write` 只捕 `OSError`/`ValueError`，任何其它异常会**杀死写者线程**，此后每次受理都
   变成静默丢弃——现在写者在单条记录的异常上记一次 `dropped` 后继续。
4. **R4 健康脚本去敏**：异常原文与 payload repr 全部移除，改为封闭静态类别；顺带修掉一个真实
   归类错误——`urllib` 把证书失败包成 `URLError(reason=SSLCertVerificationError)`，只捕
   `ssl.SSLError` 会把它误报成 `unreachable`，现在按根因归类（真实 TLS 回环用例锁住）。

阻塞——事件循环停在 `_to_stderr` 里，此后所有请求、`/healthz`、后台轮次都不再推进，进程仍

配了 `TIANSHU_LOG_DIR` 时同一序列 0.03 秒内回答，没有日志目录时才冻结——所以它只在"默认
开发路径"下发作，这正是首验与本地都踩到的那条路径。

### 修复方式（产品代码，不是放宽断言）

1. 诊断通道（标准错误）改由适配器**自己的写线程**（`tianshu-log-stream`）写，与分段文件同一
   模型：有界队列 + 单写线程。
2. 该通道**设为非阻塞**（`os.set_blocking`），写不进去的记录计为 `dropped`——`emit` 永不
   等待读者，也永不抛给业务。
3. 队列满时非持久通道**丢弃并计数**，不拒绝业务：该通道本身已让进程 `not_ready`，把"没人读
   的调试流"升级成服务中断并不更诚实。持久通道仍执行严格规则（写不进去即拒绝业务 503）。
4. 顺带修掉一个真实竞态：待写计数曾在**入队之后**才发布，写线程可能在入队瞬间就完成该记录，
   于是 `flush()` / `admit()` 会读到 0 并把尚未落盘的记录报成"已到静默点"。现改为入队前发布，
   失败时回退计数。

## 4. 风险与未完成

1. **镜像未构建**：`Dockerfile`、`.dockerignore`、健康检查脚本只做了静态检查（含"必须声明
   HEALTHCHECK / 非 root / exec 入口 / 不含凭据与模型下载"的断言），没有真实构建或启动。
   健康检查脚本本身已用真实回环 TLS 监听验证。
2. **标准错误无人读取时丢记录**：非持久通道的队列写满即丢弃并计数（`dropped`）。这是刻意的
   取舍——绝不阻塞事件循环——但意味着"用 `subprocess.PIPE` 捕获运行进程的标准错误却不读"
   这种用法会丢日志。生产应让标准错误落到运行时可读处，或用 `TIANSHU_LOG_DIR` 走文件通道。
3. **`dependencies=not_verified` 是永久的**：本批没有任何真实依赖可验证；下一张卡接真实
   Memory/网关/渠道时才可能变成 `ok`。
4. **日志预算策略是"拒绝业务"**：容量写满即 503。若运维希望"降级但继续服务"，需要新卡明确
   改这条语义，而不是在本卡里放宽。
5. **`flush()`/`admit()` 的静默点语义依赖"入队前发布待写计数"**：改动这一处会重新引入
   "尚未落盘却报已到静默点"的竞态（返修轮修掉的第二个真实缺陷）。`tests/test_observability.py`
   的 `test_a_quiet_point_is_never_reported_while_a_record_is_still_queued` 锁住它。
6. **终态 `fsync` 的代价在写者线程上**：终态事件每次多一次 `fsync`（实测合成 0.25 秒的
   `fsync` 下事件循环心跳仍是 0.016 秒）。若将来事件量把写者压满，表现为受理变慢/队列满拒绝，
   而**不是**事件循环卡住；调 `drain_seconds` 或改用批量策略需要新卡明确。
7. **关闭超时是"未确认"，不是"已关闭"**：`close()`/`aclose()` 返回 `false` 时，句柄仍由写者
   持有、在途计数保留原值、进程可能仍有记录在写。调用方必须把它当报告看，而不是当清理完成；
   进程退出前若想确认，应等写者结束后再调一次（第二次调用会重新判定，不会返回过期的 `false`）。
8. **健康检查类别是封闭枚举**：新增失败种类必须同时改脚本与 `docs/runtime-events.md` 第 8 节，
   不允许临时把异常文本塞进输出。
9. **停止是一份状态，因此没有"从外面把写者踢出去"的手段**：满队列不再吞掉停止请求（第三次
   返修 R1），但代价是写者只在完成当前这条记录后才会看到停止。如果一次底层写入永久挂住
   （不是慢，而是永不返回），`aclose` 会如实超时，写者线程会一直存在（它是非守护线程），
   进程退出取决于解释器对非守护线程的处理。真正的兜底是操作系统层面的终止，本卡不假装
   `close()` 能取消一次已经在内核里的写入。
10. **未做**：数据库迁移、网页/引擎/锁改动、真实部署、推送。
