## 改动与复用

- `Core._prepare_context` 复用既有 `VerificationCheckpoint` 和逐 check 的 verified 字典。同一次准备的依赖与多个历史候选共享成功的精确授权/来源读取；候选失败时关闭并 drain 原图，为原有整组 input-only fallback 创建新 checkpoint；最终在 finally 中关闭。生成前、模型恢复前和每次发送仍独立 fresh 核验，保留 Q16 await 后重读持久取消/终态的修复。
- 在历史和迟后 profile 批次前按实际 `source_deadline` 判断剩余租约，20 秒以内才调用既有 `continue_delivery_origin`，随后重新确认当前 scope、channel、binding、角色与本地来源/取消。20 秒沿用已有来源核验阈值，覆盖现有 15 秒查询预算；没有修改 60 秒 TTL、吞掉 403 或生成本地延期。续租更换准备 checkpoint；历史来源缓存键同时绑定实际租约 deadline，长准备不能无限复用上一次租约证明。并行来源续租后重读持久来源和 deadline。
- MemoryLearning 继续使用原 metadata 队列、job、output、receipt、deadline 和公平扫描。`attempts` 保留全部预约证据，增加持久失败分类：`rate_limit`、`receipt`、`temporary` 各最多 6 次失败，语义 `proposal_failures` 仍最多 3 次；全局最多 18 个预约 attempt。`commit_wait` 沿用已预约 attempt，等待本身不额外计数；旧任务没有分类证据时把旧 attempts 保守计入 temporary，不重置。
- 初始 null-output receipt/content 读取的 `unknown` 超时只消耗 receipt 预算，不代表曾提交，也不消耗语义拒绝次数。每次都先查询同 job；完成就采用 receipt，读取失败不能提交或重新生成。有持久 output 时，只在有效 Memory pending 响应后继续原 job 的完全相同 output。明确 rejected 才可清 output 并在既有三次语义预算内重提取。
- `JsonService` 保留合法 HTTP `Retry-After` 的秒数/日期下界；正下界交给持久任务，不立即重试。MemoryLearning 用 max(既有退避, Retry-After) 保存 deadline，不占住 worker/model slot 睡眠。压力标记仅是 hint，不是模型恢复授权。
- HTTP 429 与 typed 限流现在共用 `Gateway._rejected_rate_limit` 的同 request/config/caller 终态核验；仅明确 failed/failed/upstream_http_error、未取消、没有 finish/tool 事实才能置 `retryable_model`。Core 仍用 Q16 唯一一次 `model_connection_retries`，HTTP 后又 typed 失败也不会有第三次生成；持久发送、工具、取消及 fresh 来源/角色/租约门槛保持。前台等待取 max(原 0.2 秒, 有效 Retry-After)，等待后重新读持久状态并核验，仍受原 180 秒生成预算约束。
- MemoryLearning 在回执读取、后台槽位、模型选择及提交锁等待后重读当前源轮，复用 `sources_current`、角色和 capability 检查；取消/撤源/撤权阻止新模型或写入。`commit_wait` 的持久屏障只保留到慢 receipt await 结束；读取失败/取消后的冷却按原行为释放屏障，保留 output 和重试证据，避免新增群聊冻结。

## 限制与下一步

Memory 精确基线 `84c2f56` 的 `CandidateExtraction.execute` 先查同 job 的 write_ledger，`TrustedWorkflow._commit_candidate` 在事务内以 job 和 drafts digest 单次消费并返回原结果，所以有效 pending 后重试 exact output 不会生成另一任务或事实。但协调者已确定性复现初始 ledger 与 `_content` 间旧 unknown 提交落库、重放误报 rejected 的竞态；本卡不改 Memory，也不自行放宽 rejected，必须与本批 Memory 的拒绝前 ledger reconciliation 根修联合验收。

现有 ModelSlots 提供容量与前后台公平授权，没有 provider 级 cooldown。本卡保留逐 job 持久退避和既有每四次选择至少一次 due retry 的公平性，仍可能有同 provider 集中 429，不能把提高硬界或内部额度当成供应商恢复。前台遵循 Retry-After 的等待仍持有原模型槽位，受原 180 秒总预算限制。本卡只证明 consumer 收到有效 Retry-After 时遵循；固定 Gateway 非 2xx 分支并未证明保留上游 header，不能称 OpenCode→Gateway→Core 的完整透传已验证。真实 122 条完整百人混合 PG/DeepSeek 的调用数、429/超时、最终交付与后台收尾由协调者统一验证；本卡组件通过不代表这项已通过，也不代表 storage 0.1.2/PG 联合已通过。

根当前合同与 Q16 冻结版本不同，本卡始终使用真实冻结合同路径，没有修改共享合同或伪造 workspace context。生产保持既有 Q15，不涉及 Gemini、模型额度、用户记忆、QQ、设备或媒体挂载。
