## 问题与修改归属

原 `JsonService.stream` 在异步生成器内用 `asyncio.timeout(120)` 包围 `yield`。消费方 `Gateway.complete` 收到一个片段后会等待本地 `on_delta` 投递回调。若定时器在生成器暂停、回调等待时到期，取消会发生在消费方，而生成器内的 timeout 没有机会将它转换成 TimeoutError；`Core` 按真实外部取消重抛，可能留下持久的 `generating/stream_open`。同会话随后出现的 `commit_wait` 又会等待该活动轮次，阻止后续认领。

第二轮真实请求 q53 的模型端 8.204 秒内完整返回 HTTP 200，但其多个逐段核验延续到约 120 秒，最终仍为 `generating/stream_open` 且无 failure。该时序与上述缺陷强一致；没有捕获其当时 live task stack，因此不冒称实际取消事件已有直接堆栈。根协调者持有该次完整失败记录。

纯 asyncio 同形复现位于前任务树 `.runtime/q18-stream-cancellation-repro.py/json`，五个断言确认旧结构泄露 CancelledError、新读取边界保留真实外部取消。这是加速控制流证明，不是实际模型请求重放或性能测量。

本卡沿原流读取实现修复：标准库 `AsyncExitStack` 管理响应生命周期，连接及响应头、每次网络迭代的 await 共用累计 **120 秒**余额；每次 await 后扣除实际耗时。`yield` 时没有仍生效的 timeout，慢本地投递回调不再消耗供应商网络等待预算。原 HTTP **30 秒**设置、SSE 解析、响应字节预算、断流/部分内容/工具输出的恢复标志与真实外部取消语义保持原路径。没有改变 Core、模型容量、租约或日常 Gemini。
