# TS-339：模型生成身份与前后台容量一致

本地候选，未集成、推送或部署。分支 `codex/unified-companion-20261027`，基线 `677fcb1f1392c134084d6e2be0d61f1a49f757b4`。仅修改 Companion 的模型选择/学习/图像装配接点及相应用例，不改变聊天状态机、记忆账本、权限合同或 ComfyUI。

## 问题与改动

自动 MemoryLearning 已占用本地 `models.background`，但两条实际模型路径仍使用前台选择器和 `core.gateway`。Gateway 的前后台 class 来自认证 service 的部署登记，不来自 `X-Tianshu-Workload`；因此本地后台名额不能证明 Gateway 的全局及每供应商后台上限生效。

新自动学习任务现在复用 Life 已有的独立背景 Gateway、selector 和 caller，选择请求继续使用真实源 scope、`function_id=memory`。schema3/4 的保留提案路径与 schema5/6 的上下文路径使用同一个 `_pin_model`。本地仍使用原 `models.background`，来源核验、阶段公平、候选 IO 锁、持久输出及 unknown 回执恢复不变。取得模型槽后先核验既有自动阶段许可，再持久化路由与请求 selector；排队期间新出现的前台需求仍可让后台阶段原样退让，不花重试额度。

Platform 原有 `ProviderAuthority` 的 grant 以 `turn_id` 为键，并核验整个选择请求摘要；同一 ID 换 caller 会产生真实 `version_conflict`。本次没有更改该权威语义。初始化时在原 metadata 保存一次 rowid 高水位：既有任务继续使用原前台 caller 和生成 ID；新任务在首次选择前随原任务持久化 `model_route={caller_service,turn_id}`，背景 ID 加入实际 caller。以后重启或移除背景配置仍保留该身份；缺失原身份时明确失败，不改 ID 绕过已启动模型的 unknown 结果。历史任务继续计入前台 Gateway 预算，不能宣称全部迁移。job、event、material、receipt、attempt 与保留 proposal 的身份及内容没有改写，仍先恢复回执。

高水位不是 SQLite 隐含特例：原 `storage_postgres.py:201` 为 metadata 等表声明 `rowid BIGINT GENERATED BY DEFAULT AS IDENTITY UNIQUE`；`:210`、`:230`–`:238` 的原迁移保留 rowid 并把序列推进到最大值之后，原 `Store.put` 的冲突更新不改 rowid。PG 方言保留本次 MAX(rowid)/主键查询的相同语义。本轮做了源码核对，没有连接真实 PG 验证。

图像编译原来通过 Life 的背景 selector 取得 grant，却通过前台 Gateway 执行，独立背景配置下两者身份可能不匹配。现在网页管理与聊天工具明确使用前台 selector/Gateway/slots，自主活动和主动照片沿内部 `background=True` 使用背景三件套。新的图像选择 ID 同样包含实际 caller，避免复用另一 caller 的旧 grant；原 image-preparation marker 在编译前已持久化，completed 继续复用结果，preparing/unknown 仍拒绝重新编译，不更换 ID 绕过不确定结果。`model_slot_held=True` 仍通过 nullcontext 复用调用者已占的那个槽；不会在单槽部署中等待自己。实际 GPU submit/poll、原件与 job 幂等规则不变。

Life 原有的选版/租约判断收束为 `model_selection.pin_generation`，由 Life、自动学习和图像的生成装配复用。独立身份必须有自己的合法动态选择器或原已有 `life_config_version`；不会借前台动态 grant 或深拷贝聊天 turn 的配置。旧部署没有 background 服务时保留原前台 Gateway/选择器兼容路径；这种部署只保证 Companion 本地后台上限，**不能声称 Gateway 已按独立背景身份预留容量**。未增加权限、配置开关或通过 workload header 伪装 class。

## 调度梳理与仍有的边界

Companion 当前7个独立 asyncio 后台循环：core.tick 50ms、memory.work 1s、life.work 2s、images 2s、writing 5s、proactive 2s、direct 0.5s。聊天准备与模型容量分别有界，会话最多2个活跃 turn；发送仍用每会话 send band 和不可变表达/分段身份。Memory→Companion source_facts、Knowledge 原件核验等回调需要可重入，统一宿主不能把整个模块请求或整个会话生成放在一个持锁等待依赖的队列里。

本卡没有改以下只读定位到的串行点：Store 在 loop 上执行同步 SQLite/PG 事务（SQLite busy_timeout 5000ms）；图片原件阶段同步 hash/write/fsync；Proactive.work 持全局 lock 等待已有回执、主动表达和图片准备，会延后独立提醒；Writing.work 的全局 lock 覆盖完整模型等待。Life 已按 actor 调度并轮转阶段，不应再加全局生活队列。这些点应由后续统一宿主任务按实际短事务/CAS及外部 IO 分界处理，不与本卡的认证/预算修复混写。

没有执行生产 PG、真实模型、QQ、GPU、NAS、Linux 容器或统一 host 的实机验证；没有测量吞吐/资源节省，也未宣称这些调度边界已全部消除。
