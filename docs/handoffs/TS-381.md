# TS-381 陪伴、记忆、资料、日程业务链路

Companion 基线：线上 R7 `340cb78cf8bb6d9bb16c1b344fac8d85dc43e2d1`。分支 `codex/chain-domains-20261028`。Memory 配对提交 `6ae7a1adfd8fb2ed5ee7d92a3ee5819e230678f9`（产品源优化提交 `81b006f0c6a7077eb17d87945aa91dd747a2da39`，其 R7 基线 `abe78da4293ac679f38d41e13c346ad51c9a5fbf`）。本交付仅本地隔离开发；协调者另行构建 Linux wheel、单容器 owner-loop 验收与串行集成。

## 确认并修复的根因

1. **提醒/主动联系回执永久饥饿**：原来每轮固定取最早四条 unknown/queued/sending，四条一直无结果时第五条永远不查。改用原 `Proactive._rotating_scan` 的持久游标及原 Store.get_many；每轮仍最多四条。四个互相独立的原 expression 回执复用 `read_parallel` 并发读取、取消后等待全部清理。所有回执处理结束后才重新判新联系的 quota/cooldown，保持实际记账顺序。没有重发原发送或增加模型并发。
2. **关系 outbox 选择与执行不一致**：调度曾选择一条 row，实际 flush 再取全局最早 row，可能执行另一个被暂停房间的内容。暂停头/暂停页也可能阻挡其他房间。现按原有 64 条有界游标寻找可运行 row，并把该 exact row 交给 flush；flush 重读该 row 的状态和 deadline，失效时不换一条执行。相同 actor/会话的较早 pending/submitting 继续阻挡后继，轮转不会造成越序；unknown 仍保持原有不自动重放规则。Memory 仍唯一拥有关系/好感/冻结账本。
3. **后台执行关联断开或借用前台生命周期**：自动 Memory phase、actor life phase、主动联系 pass/回执查询各有独立随机 correlation。outbox 在已有后台 scope 中保留该 scope，不再强行覆盖成已完成聊天的旧 ID。没有第二份关系/记忆/任务账本，没有派生用户身份或原文进入日志。
4. **实际读取/回复缺少清晰观测边界**：在原诊断适配器登记 `turn.memory.*`、`turn.knowledge.*`，并补齐原生 `turn.delivery.*`。记录真实调用、响应 schema/version/hash/receipt 核验和 perf_counter duration；不读取资料的轮次没有资料读取事件，queued/sending/unknown 不记成功。原消息、权限、版本、取消及发送不重放规则未改变。
5. Memory 同号提交修复同文本子查询重复 embedding、facts/episodes 不相关检索及 Memory owner 出站 correlation，详见其同号交接。
6. **自动 phase 结果误读旧对象**：关系 flush 为 exact id 重新取 JSON 后，调度层仍用执行前对象判断终态。改为按原 family/id 读取一次持久行；关系与 actor-memory 的 delivered/unknown/submitting、学习 completed/invalidated、旁听材料 accepted/rejected 分别投影。真实终态优先于取消/last_error，未知不画确定失败；诊断读取失败只报 unknown，不遮盖原结果或触发重试。

## 诊断事件的精确含义

全部仍为原 diagnostics/v1 的 12 闭合字段，没有原文、人物/会话标识、URL、凭据、任意 extra 或新跨度账本。

| 事件 | 含义与限制 |
| --- | --- |
| `turn.memory.started/finished` | 首次实际 Memory.query_context/select 及其响应投影。成功只证明本次读取通过，不证明召回非空或写入了事实；验证阶段依然使用各自新 checkpoint。 |
| `turn.knowledge.started/finished` | Reading.owner(read) 或原件读取路径，含 schema/available_until/version/hash 核验；本地 Companion 作品/图片不伪造 Knowledge 读取事件。 |
| `turn.delivery.started/finished` | 实际 legacy send 或 native send_expression，含回执持久处理；sent→succeeded，partial→degraded，queued/sending→unknown，未知发送/取消发送→unknown。finished 带真实 duration。 |
| `memory.phase.started/finished` | 当前实际自动处理 phase，独立后台 ID；按 family/id 持久终态投影。completed/delivered/actor_memory_delivered/material_accepted 表示该阶段成功；invalidated/来源拒绝表示取消，unknown/submitting 保留未知，普通 pending 为 degraded。材料受理不是事实保存，每个候选也不必增加事实或好感。 |
| `proactive.reconcile.started/finished` | 原投递回执恢复；没有回执或取消读取仍 unknown，不宣称原发送取消/未执行。每个查询拥有独立后台 ID。 |
| `proactive.delivery.started/finished` | 原提交意图落盘后发起一次实际派发，只有真实返回状态决定结果；不等于生活或图片产物生成成功。 |
| 原 `turn.generation.*`、`outbox.flush` | generation 为整轮原生生成/工具处理包络，不是某次 Gateway RPC 的证明；outbox 共用于候选受理/来源修复/关系结算，不能当事实已保存或分数增加。 |

观测图应继续只按实际记录展示；没有明确事件的步骤标未观测，不能由服务 HTTP 成功推断领域产物成功。后台任务不补发前台 `service.request.finished`。

## 本地合成结果

- 九条一直 unknown 的真实持久 attempt 在三轮有界扫描内均被读取；原实现永远只能碰到前四条。测试同时卡住四个独立回执证明并行上限为四，取消后活动读取归零，attempt 原文逐项不变，无一次重发。
- 70 条暂停关系记录不会饿死另一个房间；实际 flush 只执行已获准的 exact row。另有同一房间较早 pending 未完成时，游标不能让后继越序的回归。
- 记忆后台 model/candidate 调用保持一个真实 phase ID，与先前前台 ID 不同；读失败阻止模型/回复；资料撤销后没有读取成功事件；原生 partial/unknown 回执不会被画成回复已送达。
- 关系真实 delivered、丢 ACK、来源拒绝、等待 ACK 时取消均按持久 exact row 观察；取消时已经存在的未知结算仍 unknown且不重放。actor-memory 在 lost ACK 后为 unknown，重启后只查原 key 回执并正确显示 succeeded；材料受理、拒绝与学习来源失效也有实路径断言。
- 同文本多子查询的纯向量派生从三次降为一次及新请求撤权证明见 Memory 同号交接。这些是合成正确性/调用数证据，不是线上延迟承诺。
