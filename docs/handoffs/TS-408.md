# TS-408 后台记忆恢复与自主失败定位

基线：`5b83948c507fba97a496cfda1acff882816aff7f`。分支：`codex/ts408-runtime-recovery-20261029`。本卡只本地提交；协调者负责配置、集成和生产操作。

## 根因与范围

协调者生产只读证据 `companion-recovery-20261029/gateway_state-result.json`：Gateway `max_in_flight=16`、`max_provider_in_flight=4`、`interactive_reserve=4`，每供应商后台容量为零；background admitted 为零，cancelled 43、deadline_exceeded 4。四个旧模型请求均在排队阶段取消。Memory 的四个 schema 6 作业 pending、已有 batch、没有 ledger；Companion 六次失败后 blocked。

因此不扩大 30 秒模型总预算、不改租约下限、不改模型或权限。Gateway requests 尚无行不表示未到达 Gateway：排队只在进程内，开始上游后才写 requests。receipt 404 本身也不证明未执行。自主 marker 原本不保存 selection/config，因此 null 不能作为选模失败证据。

## 变更与复用

- 既有 `MemoryLearning` 新增显式 owner `recover`，复用 dispatch lock、原 job 索引、`_candidate(output=None,reconcile=True)` 和原 Memory 回执/批次检查。
- 仅接受 schema 6、blocked/model、没有输出的原作业；actor、原 model request ID、attempts 和 failure_count 必须精确匹配。已有实际完成或失效回执直接收口；pending 只返回 resumed，不冒称记忆已写入。
- 在既有 metadata 保存按 actor/request_id 隔离的幂等恢复回执。一次授权仅放行一次模型尝试及其输出提交。原 attempts、failure_count、recovery_failures、first/last_failure、job_id、batch_ref、segment_id、model_route.turn_id 均不重置、不替换。再次失败即 blocked。
- 模型提交前持久化 request_id、turn_id、config_version、caller_service。新尝试有自己的 model request ID，并保留恢复授权关联的旧 ID；不能把不含正文的旧 Gateway 回执假装成可恢复模型正文。一次恢复已 submitted 而输出未持久化时，不重复使用该授权生成。
- 自主 goal marker 保存实际选择的安全元数据，复用固定机器 `failure_diagnostic` 保留请求 ID 和原因；TimeoutError 不再误标 invalid_input。不记录异常正文，不改变未知副作用语义。
- 协调者单写 `app.py` 的 platform 服务鉴权薄路由，以及 `Gateway.generate(..., request_id=None)` 透传；两处随本卡提交。
- 按协调者补充，恢复命令加入既有 lifecycle ROOT_COMMANDS，排空期间拒绝新恢复。`pin_generation` 对过期或不足原 MINIMUM_LEASE 的 retained lease 重新向原 selector 递交完全相同请求，不换 turn；Platform TS-412 负责同原 provider/revision 续发 publication，撤销/变更仍拒绝。新返回租约不足仍拒绝，不覆盖旧 pin。

无 DDL、新依赖、用户记忆结构或 actor-memory 域修改；没有改 window、core、store；没有删除有效路径。

## 恢复协议与部署步骤

仅受信 platform 服务调用：`POST /internal/v1/memory/learning/recover`。严格六字段：

```json
{
  "actor_id": "actor:example",
  "job_id": "job:original",
  "request_id": "recovery:stable-owner-command",
  "expected_attempts": 6,
  "expected_failure_count": 6,
  "model_request_id": "model:00000000000000000000000000000000"
}
```

响应：`{request_id,job_id,state,attempts,failure_count,model_request_id}`；state 为 resumed/completed/invalidated。相同恢复命令返回原回执，异参复用 request_id 为 idempotency_conflict；CAS 或请求身份不符为 version_conflict。重复 resumed 回执表示原授权已记录，不表示当前后台仍 pending；当前结果继续查原任务/Memory 原回执。

协调者执行顺序：

1. 修正已证实的 Gateway 后台零容量配置；保持用户其余有效配置。
2. 逐个旧 model_request_id 核对原 admission 的排队取消证据，核原 Memory job/batch/ledger。**该受信管理命令表达操作员已核证后的授权；接口不会把 404 自动解释为未执行。** 不对不明 upstream 执行使用此命令。
3. 核对原 model_route.turn_id 的 Platform grant/publication 仍有效。现有 select 对过期原 grant 拒绝，不能换 turn 绕过；若过期由 Platform 原 owner 的受支持授权路径处理，本卡不清授权。
4. 使用原 job 与最后失败计数、model_request_id，发一次稳定 request_id 命令。网络结果不明只重发完全相同命令，不改键。
5. 后台原 worker 继续，检查原 job 最终回执/ledger及保留的六次历史；再次失败立即保留 blocked 供原因核对，不循环授权重试。

自主 goal-choice unknown 不属于 daily-generation retry：现有每日生成 retry 路由不能处理它。AutonomousGoals 在原 autonomy_due_at 到期后依据当前状态正常进行新的纯模型目标规划，旧 unknown marker 保留，并不被宣称恢复完成；没有对旧操作直接改 state 或重放。若当前 activity 的 step_operation 为 unknown/submitted/tools_pending，原副作用保护仍阻止重规划。本次零容量修正后可等待正常自主轮次，不需要对旧 goal-choice 手动恢复。
